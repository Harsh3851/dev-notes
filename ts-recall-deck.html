1 · What TypeScript is the luggage-tag model

One sentenceTypeScript is JavaScript plus labels saying what type each thing is. The labels are checked before the code runs, then thrown away. What actually runs is plain JavaScript.

Every variable is a suitcase. JavaScript lets you put anything in any suitcase. TypeScript puts a tag on each one — "numbers only" — and the checker stops you at the door if you try to put a string in it. The tag is checked at check-in (compile time). On the plane (runtime), tags are gone.

You already write it daily: every name: string, interface and <T> in an Angular component is TypeScript.

2 · Two tools, not one checker vs runner

ToolJobReports type errors?
tscthe checker — reads labels, finds mistakesYes — this is the whole point
tsxthe runner — strips labels, runs the JSNo, never
VS Coderuns the checker live in the backgroundYes — red squiggles + the Problems count
npx tsc --noEmit --strict file.ts   # check only (no JS output)
npx tsx file.ts                     # run (no checking!)

Your ▷ button is configured to do both in order: tsc --noEmit --strict … && tsx … — the run happens only if the check passes. Type errors stop it at the door. That's the correct behaviour and what CI does later.

Your past mistake (28-09)Ran tsx on count = "five" and got "five" printed — then asked why there was no error. tsx doesn't check; the label was stripped and the string went through. That WAS the luggage-tag model, demonstrated live.

3 · Labels and inference

let count: number = 0;          // a colon, then the type — "count, which is a number"
let name: string = "Harsh";
let scores: number[] = [10, 20];  // array of numbers

let price = 10;                   // no label needed — TS INFERS number from the value
price = "ten";                    // ❌ still checked: the suitcase is tagged number
When to write the labelLet TS infer when the value is right there. Write the label when TS can't know: function parameters (always), empty arrays, things assigned later.

4 · Reading a TypeScript error the skill that matters most

basic.ts:11:10 - error TS2322: Type 'string' is not assignable to type 'number'.
11   total(["a", "b"]);
            ~~~
  • 11:10 = line 11, column 10. The ~~~ underlines the exact thing. Read the location first — it tells you WHERE the mismatch is.
  • "X is not assignable to Y" = you tried to put an X into a suitcase tagged Y. Almost every TS error is a variation of this sentence.
  • Here it points at the call — the argument "a" — not at reduce, not at the return. The parameter is tagged number[]; a string arrived.
TS never runs your codeThe checker compares labels. It does not execute, simulate, or compute anything. No reduce ran, no "10ab" was built. If your explanation of a TS error describes what the code "would do at runtime", it's the wrong explanation.
Your past mistakes (28-09)Explained the error as "+ concatenates 10 + a + b into a string, so the return isn't a number" — a runtime story for a static check; the error pointed at the argument, not the return. Also pulled price = 10 into the reasoning — a variable that never touches that function (reduce seeds from 0). Read the line:column; explain the label mismatch there.

5 · Functions

function add(a: number, b: number): number {   // params ALWAYS labelled; return often inferred
  return a + b;
}
const double = (n: number): number => n * 2;

function total(prices: number[]): number {
  return prices.reduce((sum, p) => sum + p, 0);   // TS knows p is a number — from the param label
}

Parameters need labels because TS can't guess what callers will pass. Writing the return type on shared functions documents the contract and catches a wrong return early.

6 · Objects: interface the shape contract

interface User {
  id: number;
  name: string;
  email?: string;                 // ? = optional — may be missing
}

const u: User = { id: 1, name: "Harsh" };          // ✅ email optional
const v: User = { id: 2, name: "Priya", age: 24 }; // ❌ 'age' is not in the shape
const w: User = { id: 3 };                         // ❌ 'name' is missing

function greet(user: User): string { return `Hi ${user.name}`; }
const users: User[] = [ { id: 1, name: "Harsh" } ];
users.map(u => u.nmae);                            // ❌ typo CAUGHT: Property 'nmae' does not exist
Why this matters for YOUYour most frequent JS bug class was one-letter slips — candidateS.city, citites, group.item. Inside a typed shape, every one of those is caught before running. TypeScript is the fix for your #1 bug.

type vs interface: both describe shapes; for plain objects they're interchangeable. Convention we use: interface for object shapes, type for everything else (unions — next lesson).

7 · Say it in the interview

30-second version"TypeScript adds static types to JavaScript. The compiler checks them before the code runs and then erases them — the browser only ever sees plain JS. It catches mistakes at the call site, like passing a string where a number is expected, and it gives real autocomplete because the editor knows the shape of every object. Interfaces describe object shapes, and function parameters are always typed because the compiler can't guess what callers will pass."
If asked "does TS make code safer at runtime?""No — types are erased at runtime. It makes code safer before runtime. A wrong API response still needs validation at the boundary; that's what zod is for."
