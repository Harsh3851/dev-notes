1 · Hoisting & TDZ hotel model

In simple words

Before JavaScript runs your code, it reads the whole scope and books a name for every variable and function declared there. That's hoisting — nothing physically moves; the names just exist early. What you get if you use a name before its line depends on how it was declared: var gives undefined, let/const throw a ReferenceError (the "temporal dead zone"), and a function declaration works fully. Keep the two ideas apart: scope is which block can see a name; hoisting is whether you can use it before its line.

Before running, JS scans the scope and "books a room" for every declaration:

  • var → room open, placeholder sign undefined
  • let / const → room booked but police tape (TDZ) — early access throws ReferenceError: Cannot access before initialization
  • function declaration → room fully furnished, usable above its line
console.log(a); var a = 1;   // undefined — NOT 1, NOT an error
console.log(b); let b = 1;   // ReferenceError, script STOPS here
Your past mistakesSaid "const is not hoisted" (it IS — hoisted but uninitialised); thought TDZ yields undefined (it throws); said the var version prints the future value 10; called hoisting "lexical scope". Scope = where visible; hoisting = when usable. Also: two function declarations with the same name — the LAST one wins.
Say it in the interview"Hoisting means JavaScript registers all declarations before running the code. var variables exist from the start holding undefined. let and const also exist from the start but can't be touched until their own line runs — that gap is the temporal dead zone, and access there throws a ReferenceError. Function declarations are hoisted with their body, so I can call them above where they're written."

// console.log(y);             // ❌ ReferenceError — let/const in the TDZ

const z = 20;                   // const must be given a value on the same line

// sayBye();                   // ❌ TypeError: sayBye is not a function (var holds undefined)
var sayBye = function () {};    // function EXPRESSION follows var/let rules, not declaration rules

What does console.log(a); var a = 3; print, and why?

undefined — var is hoisted and set to undefined; the assignment happens later, on its own line.

What about console.log(b); let b = 3;?

Declarations are hoisted with their body. A function stored in a const follows const rules → TDZ → ReferenceError.

2 · Errors which one, and what dies

In simple words

An error is JavaScript saying "I can't continue". If nothing catches it, the rest of the script stops. The error's name tells you what kind of problem it is: ReferenceError — the name doesn't exist (or is in the TDZ); TypeError — the value exists but you used it wrongly (calling undefined, reading a property of null); SyntaxError — the code itself is malformed; RangeError — a value out of range, like endless recursion. try/catch lets you handle an error instead of crashing; throw lets you raise your own.

ErrorMeansExample
ReferenceErrorThe NAME can't be accessedTDZ, undeclared variable
TypeErrorGot a value, used it wronglynull.addEventListener, calling undefined, [...plainObject]
SyntaxErrorFile doesn't parseobj.x: 5 — nothing in the file runs
RangeErrorStack blownrecursion with no base case
RulesAn uncaught runtime error kills everything AFTER that line. "Prints undefined" and "throws" are different outcomes — if x.y prints undefined, x existed. "Cannot read properties of null" → the bug is in the lookup that produced null, not on that line. NaN → some operand was undefined. [object Object] anywhere → an object went where a string was expected.

} catch (err) {
  console.log(err.name, err.message);     // "SyntaxError" "Unexpected token ..."
} finally {
  console.log("always runs");             // cleanup — runs either way
}

function withdraw(balance, amount) {
  if (typeof amount !== "number") throw new TypeError("amount must be a number");
  if (amount > balance) throw new Error("Insufficient funds");
  return balance - amount;
}

3 · Coercion & the + rule

In simple words

Coercion is JavaScript quietly converting a value to another type so an operation can work. + with any string joins as text; the other maths operators (- * / %) convert to numbers. == converts types before comparing; === doesn't, which is why you always use ===. In an if, every value becomes true or false — and exactly eight values count as false.

The rule+ is the ONLY arithmetic operator with a second job: if either side is a string it CONCATENATES. Every other operator (- * / %) forces numbers.
"5" + 1       // "51"
"5" - 1       // 4
"10" + 5 - 5  // 100  ("105" first, then minus)

textContent always returns a string → Number(x) before maths. The 8 falsy values: false 0 -0 0n "" null undefined NaN. Use === always. Say "coerce", not "reduce".

Your past mistakeSaid "5" + 1 is 6 ("converts before any calculation") — the + exception IS the question.
Say it in the interview"=== compares value and type with no conversion; == converts first, which gives surprises like '1' == 1 being true — so I always use ===. And + is the only maths operator that also joins strings, so if either side is a string it concatenates; every other operator converts strings to numbers."

4 · this the caller fills it in

In simple words

this is a hidden input to every regular function, filled in by whoever calls it. Called as obj.method(), it's obj. Called bare, or handed to something else — setTimeout, forEach, an event listener — the caller decides, and it's usually not your object. Arrow functions have no this of their own; they use the this of the code where they were written. So: regular function → look at the call. Arrow → look at where it was written.

The two rulesRegular function: this = decided by the CALLER at call time ("who calls it — anything left of the dot?"). Arrow function: no own this — borrows from where it was WRITTEN, permanently. For a regular function, where it was written NEVER matters.

any arrowthe surrounding scope's this

Wrote this.value++ expecting a local variable — this.x is a PROPERTY on whatever this is, never a variable. Always NAME the value ("this is window"), never "this is lost". 03 Oct: said a setTimeout callback is "auto-invoked", which names no caller: the TIMER calls it bare, so in Node this = the Timeout object. Said an arrow borrows this from its "parent". Say "from the function it was written inside": objects never give arrows a this.
Say it in the interview"In a regular function this depends on how the function is called — whatever is left of the dot at the call site. Called bare it's window, or undefined in strict mode. Arrow functions have no this of their own; they use the this of the place where they were written. That's why arrows fix a callback that loses this."

5 · DOM selection, fn vs fn(), events

In simple words

The DOM is the web page as a tree of objects that JavaScript can read and change. Every DOM task is three verbs: grab an element, change it (text, classes, attributes), or listen for an event on it. Events bubble up from the clicked element through its parents, so one listener on a parent can handle clicks on all its children — even children added later. That's event delegation.

Two selector familiesgetElementById("btn") / getElementsByClassName("item") — the method name says how it searches, so pass the BARE name. querySelector("#btn") / querySelectorAll(".item") — you write a CSS selector, symbols included. Use the querySelector family for everything.
btn.addEventListener("click", handleClick);    // ✅ reference — install the doorbell
btn.addEventListener("click", handleClick());  // ❌ runs NOW, registers undefined
btn.addEventListener("click", "handleClick");  // ❌ a string — TypeError
  • Multiple listeners run in registration order; onclick= is a property — a second assignment overwrites the first.
  • removeEventListener needs the SAME function object — an inline arrow can never be removed.
  • e.target = where it started (fixed); e.currentTarget = whose listener is running. Events bubble UP through ancestors.
  • querySelectorAll → static NodeList; getElementsBy* → live HTMLCollection. Neither is a real array.
Your past mistakesQuoted the handler name as a string; invented an "onclick fires first" rule; forgot to select elements at all (the id→global accident); querySelector("count") without # = tag selector → null → TypeError at click time; confused getElementById with querySelector (they never combine).

6 · Closures

In simple words

When a function is created inside another function, it keeps access to the outer function's variables — even after the outer function has finished. Picture a backpack the inner function carries with it. Each call of the outer function packs a brand-new backpack. That's how you make private variables, counters, once(), memoize and debounce.

function createCounter() {
  let count = 0;              // private backpack
  return () => ++count;
}
const c = createCounter();
c(); c();                     // 1, 2 — count survives the return

A function keeps its birth-place variables alive after the outer function returns. It remembers the variable, not a snapshot. Each call of the outer function creates a fresh, independent backpack. This is the machinery behind debounce, throttle and private state.

Your past mistakeExplained closures via "heap memory" — say lexical environment kept alive. Scope = where visible; closure = how it survives. 06 Oct (loop trap): answered the test from memory of an older version (i <= 3) and so wrote 4 4 4 for i < 3. Read the bounds EVERY time and write the steps: i = 0 ✓, 1 ✓, 2 ✓, 3 ✗ → 3 3 3. Also dropped the "k" labels from the output.
Say it in the interview"A closure is a function that remembers the variables from where it was created, even after that outer function has finished. The classic example is a counter: an outer function holds let count = 0 and returns an inner function that increments it — the count stays alive between calls and nothing outside can touch it."
Scope or closure? Ask: has the outer function finished?Inner code reading an outer variable while the outer function is still running is ordinary scope. It's a closure when the inner function is handed out (return second, no brackets) and called after the outer function has finished — and it still has the variables.
fn vs fn() — printing vs returningfn is the function itself; writing it runs nothing. fn() runs it now, and the whole expression is replaced by what it returns — undefined if there's no return. Printing (console.log) is not returning. Brackets written inside a function body don't run until that body runs.
// scope vs closure — the brackets decide
function first() { const a = 10; function second() { console.log(a); } return second(); }
first();             // runs second WHILE first is running → just scope

function first2() { const a = 10; function second() { console.log(a); } return second; }
const fn = first2(); // first2 has FINISHED
fn();                // 10 → second still remembers a: that's the closure

// one call to the outer function = one backpack. Assigning only shares it.
const a = makeCounter();  const b = a;     // ONE counter, two names → a(); a(); b() gives 3
const c = makeCounter();                   // a new call → a new, independent count

// once(fn): state in the factory, decision in the wrapper
function once(fn) {
  let called = false;              // lives in once's body: created once
  return () => {
    if (called) return;            // already ran → do nothing
    called = true;
    return fn();                   // brackets: actually RUN it
  };
}

// the loop trap
for (var i = 1; i <= 3; i++) setTimeout(() => console.log(i));  // 4 4 4 — one shared i, read later
for (let j = 1; j <= 3; j++) setTimeout(() => console.log(j));  // 1 2 3 — a fresh j each round

Predicted b() would print 1 after const b = a — functions are objects, so assignment shares the same function and backpack (prints 3); only another makeCounter() call makes a new one. In once: wrote return fn (no brackets, nothing ran), reset the flag inside the wrapper on every call, put flag = true after a return (never reached), then declared the flag inside the function passed in, where the wrapper can't see it (ReferenceError). 7 · Arrays: loops & the collect pattern

In simple words

An array is an ordered list. To build a new list from an old one by hand: start an empty basket, loop over the values, push what qualifies, and return the basket after the loop. for...of gives you the values; for...in gives you the keys — don't use it on arrays. map and filter are this same pattern, pre-built.

for...IN vs for...OFfor...in → Indexes/keys (as strings!). for...of → the values. For arrays you almost always want of.
function cheapInStockNames(products) {
  const basket = [];                    // 1. basket INSIDE, fresh per call
  for (const product of products) {    // 2. loop the VALUES
    if (product.inStock && product.price < 1000) {
      basket.push(product.name);        // 3. push what qualifies
    }
  }
  return basket;                        // 4. return AFTER the loop
}

Sibling — the sum pattern: let sum = 0 inside, sum += … in the loop, return sum after. Same skeleton, number instead of array.

Your past mistakesUsed for...in and treated the key as the object; returned inside the loop → only the first match; declared the basket OUTSIDE → results doubled on a second call; forgot return basket; called the function with no argument, so the parameter shadowed the global and was undefined. Name the loop variable product, never i, and always const.

8 · filter · map · reduce the interview trio

In simple words

Three questions. filter: keep this item? (same items, fewer of them). map: what does each item become? (same count, new values). reduce: combine everything into one result — a number, a string, or an object. All three return something new; the original array isn't changed. Chain them: filter first, then map or reduce.

The three questionsfilter — keep this one? (true/false) · map — what does each one BECOME? (same length, always) · reduce — fold everything into ONE value. forEach returns undefined — side effects only. None of them mutate the original.
products
  .filter(product => product.inStock && product.price < 1000)
  .map(product => product.name);

cart.reduce((total, line) => total + (line.price * line.qty), 0);
//           ↑acc FIRST, item second       the SEED is reduce's 2nd argument ↑
  • Chain order matters: each step's output is the next step's input. Map to names first and price/inStock are gone — filter first, reshape last.
  • reduce law: the callback's return becomes acc for the next round (map's sibling law: the return becomes the new element — a block body needs an explicit return).
  • No seed? reduce uses element[0] as the first acc and starts at element[1] — on objects that gives "[object Object]23"; on an empty array it THROWS. Always pass the seed.
  • Count-by: counts[c.city] = (counts[c.city] || 0) + 1; with seed {} · Group-by: first-time key starts as [], then push on its own line (never assign push's return — it's a length).
The object-accumulator family — one pattern, three goalsAll three are reduce with a {} seed and the line acc[key] = (acc[key] || default) + contribution. Only the default and the contribution change.
PatternStart (seed)The line inside reduceResult shape
count-by{}counts[key] = (counts[key] || 0) + 1;{ a: 3, b: 1 }
sum-by{}totals[key] = (totals[key] || 0) + item.amount;{ Asha: 1600 }
group-by{}if (!groups[key]) groups[key] = [];

Every one of themends the callback with return counts; (the inner return passes the object to the next round) and the function needs return arr.reduce(…) (the outer return hands the result to the caller). || 0 turns "no slot yet" (undefined) into 0. Never write groups[key] = groups[key].push(x): push returns the new LENGTH.
Why || 0 is not optionalOn the first round the key doesn't exist, so acc[key] is undefined — and undefined + 1200 is NaN, which then poisons every later round ({ Aman: NaN }). The || 0 supplies the starting value, and only round one ever uses it. ?? is the more precise operator (falls back only for null/undefined) and is safer when 0 is a legitimate stored value.

Sort

[10, 1, 5, 20].sort()                // [1, 10, 20, 5] — compares as STRINGS

Dedupe · flatten · recursion

[...new Set(nums)]                           // unique values, first-seen order

function flattenDeep(arr) {
  const basket = [];
  for (const item of arr) {
    if (Array.isArray(item)) basket.push(...flattenDeep(item)); // vertical: delegate
    else basket.push(item);                                     // BASE CASE: no self-call
  }
  return basket;
}
Recursion in one breathA function calling itself on a strictly smaller piece, plus a floor. Loop = horizontal (this level); recursion = vertical (into a box). It stops because each self-call is one level SHALLOWER and depth is finite. The base case is the branch with NO self-call — not the loop ending.
Picking the tool — the question decides itfilter = keep some (judged on ONE item alone) · map = transform each (same count) · reduce = combine many into one · sort = order them. "Which one is biggest?" is a comparison — an item can't know it's the biggest by looking only at itself — so it's reduce (compare two, keep the winner) or sort then [0]. Never filter.

9 · Debounce & throttle closures + timers

In simple words

Both stop a function from running too often when events fire rapidly. Debounce waits until the events have stopped for N milliseconds, then runs once — right for a search box. Throttle runs at most once every N milliseconds while the events continue — right for scroll or resize. Both are a function that returns a new function, keeping a timer or a gate flag in a closure.

One lineDebounce runs once AFTER the burst ends (wait for silence — the lift door resets on every new person). Throttle runs at most once per interval DURING the burst (the toll gate). Debounce for a search box; throttle for scroll, resize, button-spam.
function debounce(fn, delay) {
  let timerId;
  return function (...args) {
    clearTimeout(timerId);                          // cancel the pending run
    timerId = setTimeout(() => fn.apply(this, args), delay);  // fn INSIDE the timer
  };
}

function throttle(fn, limit) {
  let open = true;
  return function (...args) {
    if (!open) return;                   // DROPPED — never queued, args lost
    fn.apply(this, args);                // fn runs IMMEDIATELY
    open = false;
    setTimeout(() => { open = true; }, limit);  // timer's ONLY job: reopen
  };
}

Both are a factory (runs ONCE — creates the closure state) returning a wrapper (runs on EVERY event — makes the per-call decision). Per-call decisions can only live in the wrapper. ...args is rest (gathers); fn.apply(this, args) forwards both — note the comma, not a dot.

Your past mistakesPut the gate check in the factory; put fn inside the reopen timer (that's "delay everything", not throttle) — and it cost you a failed cold rep; wrote fn(this, args) and fn.apply(this.args); called dropped calls "waiting" (they're discarded); asked "is this correct?" instead of running the harness. Harness expectation: exactly TWO run lines. 02–03 Oct rebuild: blank on both shapes; throttle barrier set BACKWARDS (wait = true inside the timer, so it never lifts); a bare fn line (names it, never calls it); measured the 3rd debounce call from the 2nd call instead of from 0 (use ONE clock: each row = call time and call time + delay); copied an old table row without re-reading it; deleted the log(4) test line, which is the only line that proves the barrier lifts. function secondLargest(nums) {          // O(n) time, O(1) space — the answer they want
  let largest = -Infinity, second = -Infinity;
  for (const n of nums) {
    if (n > largest) { second = largest; largest = n; }
    else if (n > second && n !== largest) { second = n; }   // !== skips duplicates
  }
  return second === -Infinity ? null : second;
}

11 · Event loop · promises · async/await the one worker, two boards

In simple words

JavaScript does one thing at a time. Slow work (timers, network requests) is handed off, and when it finishes, its callback waits in a queue. Promise callbacks wait in a fast lane (microtasks); timers wait in the normal lane (macrotasks). After the current code finishes, all microtasks run, then one macrotask, and so on. A promise is a placeholder for a value that isn't ready yet; async/await is a cleaner way to write code that waits for promises.

The modelONE worker with a to-do list. Slow jobs go to an assistant; when they finish, the assistant posts a note on a board — it can never interrupt the worker. Two boards: ⭐ urgent (promise callbacks = microtasks) and 📋 normal (timers, clicks = macrotasks). The worker's rule: finish my list → clear the ENTIRE urgent board (including notes added while clearing) → take ONE note from the normal board → repeat.
console.log("1");
setTimeout(() => console.log("2"), 0);
Promise.resolve().then(() => console.log("3"));
console.log("4");
// 1 4 3 2  — own list, then urgent, then normal

setTimeout(fn, 0) is not "now" — it means "post the note immediately", and the note is still read last. Node extra: process.nextTick is an even-more-urgent lane.

Promises

A promise is a token for a value that isn't ready. States: pending → fulfilled | rejected; it settles once. .then returns a NEW token, and your callback's return value rides forward — the same law as map (becomes the element) and reduce (becomes the acc).

function wait(ms) {
  return new Promise((resolve, reject) => {   // resolve/reject are the two levers
    setTimeout(() => resolve("done"), ms);      // pull ONE, once
  });
}

Promise.all([a, b])   // all fulfil, or fail fast on the first rejection
Promise.allSettled()  // never rejects — status objects
Promise.race()        // first to SETTLE · Promise.any() — first to FULFIL

async / await

async function main() {          // async = permission slip; always returns a promise
  try {
    const msg = await wait(1000);  // await = unwrap the token; PAUSES THIS FUNCTION only
    console.log(msg);
  } catch (err) { ... }           // a rejection behaves like a throw here
}
The pauseA pause button on the recipe, not on the kitchen. The rest of the program runs during it. An async function runs synchronously up to its first await; everything after it is a microtask. Two independent awaits in a row run SEQUENTIALLY — use await Promise.all([a(), b()]) for parallel. forEach(async …) never waits.

13 · Prototypes & class the ask-your-parent chain

In simple words

Every object has a hidden parent, its prototype. If a property isn't on the object, JavaScript looks in the parent, then the grandparent, and so on. That's how every array shares one map. A class is a tidy way to write a constructor plus methods that live on the prototype; extends sets up the parent chain, and super calls the parent.

The modelEvery object has a hidden link to a parent object — its prototype. Looking up a property: ask the object, then its parent, then the grandparent, until found or null (then undefined). That chain is why [1,2,3].map(...) works: your array doesn't own map — Array.prototype does, and every array shares that ONE copy instead of carrying its own.
const nums = [1, 2, 3];
nums.hasOwnProperty("map");             // false — the array doesn't own it
Array.prototype.hasOwnProperty("map");  // true  — the parent does
